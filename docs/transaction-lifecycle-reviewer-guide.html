1 / Why change the transaction flow?

The previous implementation supported the main transaction flows, but its structure made them fragile and difficult to maintain. Execution, tracking, and status updates were spread across separate parts of the app. A change in one part could affect another, and understanding the full behavior required following several paths.

Responsibility for a transaction was divided. The transaction window controlled execution and some receipt handling. Notification code stored and changed status. Separate background checks followed source transactions and bridge delivery. Understanding one action required tracing these parts and their timing.

This branch puts the common rules in one shared lifecycle. Route-specific code still prepares the action. One sequential runner sends its steps. A tracking service follows submitted transactions outside the transaction window. A record reducer applies the results, and shared selectors decide what each view displays.

The purpose is to make a transaction easier to reason about from start to finish. The work does not redesign route selection, vault calculations, or slippage policy. It changes where execution, tracking, and status decisions belong.

2 / How the new transaction flow works.

Prepare. Send. Track. Show. Each part has a purpose, and each part hands a defined result to the next.

Preparation selects the route, calculates amounts, obtains a protected quote, and prepares the next wallet action. It remains specific to the deposit or withdrawal route. A simple vault deposit and an Enso route do not need the same preparation code.

Execution follows the reviewed sequence one step at a time. The lifecycle service uses the existing executeTransactionPlan runner. It checks the wallet context, requests the action, and registers the returned submission reference. It prepares a later step only when the required earlier result is available.

Tracking starts when that reference exists. The service follows the network receipt, Safe execution, or bridge delivery as required. Yearn creates the service above the transaction window, so closing the window does not end tracking.

The record keeps the submitted inputs and the facts learned afterward. A reducer is the function that applies each new result to this record. A selector reads the record and derives a status such as pending, successful, failed, or unknown. This separates what happened from how the app presents it.

The shared implementation lives in packages/vault-widget. It receives wallet access, network checks, storage, and balance refresh through host interfaces. It does not import Yearn app contexts or browser storage directly.

Yearn saves transaction records in the browser, so it can load them after a page refresh and resume tracking. yBOLD currently keeps records only in memory; a page refresh clears them. Both apps use the same rules to decide whether a transaction succeeded. Only Yearn currently saves the records needed to resume tracking after reload.

3 / Following the transaction flow.

From a reviewed goal to a saved submission

Consider a deposit that needs token approval and a bridge. The user's reviewed goal is one flow. Approval and the bridge action are its steps. Each try to run a step is an attempt. When the wallet returns a submission reference, the service creates a transaction record for that submission.

These distinctions keep partial progress clear. A confirmed approval completes the approval step, but it does not complete the deposit. The approval and bridge transaction have separate records linked to the same flow. A bridge then keeps its record as destination results arrive.

Before sending, the service checks that the prepared action still matches the reviewed request and wallet context. It requests a switch to the source network when needed. Submitted amounts, quote details, and call inputs stay fixed in the record. Later form edits cannot rewrite what was sent.

The flow keeps a stable identity while preparation changes. This matters after approval: a reopened window may now prepare the final action directly. It must still recognize the same pending flow, rather than treat the new preparation as permission to send again.

Some steps do not create a transaction record. A permit signature stays in the active session because it is not an on-chain transaction. A Safe batch, by contrast, is one submission even if it contains both approval and action calls.

Wait for the result the action actually requires

A receipt is the network's result for a transaction. For a same-network action, a successful receipt at the required confirmation depth establishes success. A Safe action also needs successful Safe execution; acceptance of its proposal alone is not enough.

A bridge has a further requirement. The source receipt proves that the source transaction succeeded. The requested deposit or withdrawal remains pending until destination delivery is established. The destination requirement is fixed when the action is submitted, so missing tracking information cannot turn a bridge into a completed same-network action.

The app asks Enso whether the bridge has completed the requested delivery. If Enso confirms the whole route is complete, the app can show success even when Enso does not provide a destination transaction hash. If Enso reports only individual steps, the app waits until it can confirm that every required step succeeded. An incomplete report cannot establish success.

A bridge may stop and require the user to take a recovery action. The app keeps tracking the unresolved result. If the funds are returned, it records the refund, but the original deposit remains failed: the money came back instead of reaching the intended destination. The user needs to know both whether the deposit worked and whether the funds were recovered.

Prepare later steps from confirmed results

The central rule for multi-step flows is to preserve completed work and resume at the step that still needs action.

A withdrawal that first needs to unstake shares follows the same sequence: unstake, confirm, determine the available shares, then prepare the withdrawal. The next action uses confirmed evidence for that unstake.

If preparation of the withdrawal fails, the unstake remains successful. Retrying preparation must not send the unstake again.

Balance refresh follows confirmed results for deposits, withdrawals, Safe actions, and bridges. Bridges refresh source assets after source confirmation, destination assets after delivery, and relevant assets after a confirmed refund. A failed refresh cannot undo a confirmed transaction. Data needed to prepare the next wallet action may still be required before that action can proceed.

Why bridge checks need shared Redis coordination

A bridge can take time to finish, so Yearn asks Enso for its status repeatedly. Many users and tabs can request these checks at once. The requests may reach different Yearn server instances, but those instances share an Enso API key and its request budget.

A timer in one browser or server cannot control the total traffic. Redis gives all server instances one shared queue and one shared time for the next allowed request. A server must claim permission in Redis before calling Enso. Redis checks and updates that permission in one operation, so two instances cannot spend the same allowance.

The server checks the oldest queued route and briefly caches the response. Other requests for that route can reuse it. If Enso asks the app to wait, Redis shares the delay across instances. The browser also gives eligible records turns to be checked, rather than repeatedly selecting only the newest transaction.

Redis therefore coordinates provider requests; it does not store the user's lasting transaction history. All deployments sharing the Enso key must use the same dedicated bridge Redis database. The normal request reservation lasts 30 seconds, cached responses last 10 seconds, and queue entries expire. Provider backoff can extend the wait.

4 / How it handles interruptions.

Closing a window pauses execution, not tracking

Once a transaction is sent, it belongs to the tracking service rather than the screen that requested it. Closing the window pauses future wallet requests. Tracking of submitted work continues, and a wallet response that arrives after closure is still registered.

On reopening, the app shows the existing progress. A paused sequence requires an explicit Continue before another wallet request. Reload can restore saved records, but not every temporary signature or prepared call. Missing preparation must be reviewed again.

Load history before allowing a new request

Yearn loads saved lifecycle records before starting a new wallet request. If it finds the reviewed action still pending, it adopts that record and resumes tracking. If loading fails or stalls, it waits and retries. Unavailable history is not empty history.

Once a submission reference has returned, live tracking starts without waiting for a successful save. A failed write must not lose the active record or permit a second submission. However, wallet submission and browser storage cannot be one atomic operation. If the reference was never received or saved, recovery after reload cannot be guaranteed.

Yearn uses IndexedDB to read, merge, and write record updates in one database transaction. BroadcastChannel shares changes between tabs, and Web Locks coordinate work where supported. Browsers without Web Locks have weaker protection against simultaneous requests from different tabs. yBOLD's session-only host does not provide Yearn's reload recovery.

Preserve known results when later checks fail

A failed network request means the app could not obtain a result. It does not prove that the transaction failed. The record retains every confirmed fact while tracking retries or asks for review. Likewise, a late pending response cannot erase a confirmed result.

If reliable results conflict, the outcome stays unresolved. The service does not choose success simply because that response arrived last. A replacement transaction also needs a validated relationship to the original request. The record keeps the original reference and treats cancellation or an unrelated replacement as a distinct result.

These rules keep retry actions specific. Recheck a submitted transaction, retry preparation, and refresh balances are different operations. None should quietly send the transaction again. An unknown outcome is not permission to repeat the action.

5 / How it handles notifications.

Recent activity in the wallet menu now reads lifecycle records. Open this menu with the address or connect button. Pending transactions appear first with a spinner on the left. When a transaction completes, the same row shows its result. The desktop and mobile lists share this behavior.

Clicking the address or connect button dismisses the current account's alert dot. That acknowledgement is saved with the record and shared between tabs, so reloading does not restore an alert already dismissed. A new transaction or changed visible result can raise a new alert. An internal balance-refresh update does not.

Acknowledgement changes the alert, not the transaction. Pending rows stay visible and tracking continues. All pending entries remain accessible even when there are more than three; completed entries fill any remaining space up to the usual three-row limit. Technical approvals still appear separately. Grouping them with their main action remains future work.

How this relates to portfolio Activity

The portfolio page's Activity tab has a broader role. It loads indexed transaction history from the server and combines it with local entries for unresolved actions and recent results not yet indexed. This branch changes the source of those local entries to the lifecycle records; it does not replace indexed history.

At cutover, old local notification history is not imported. New lifecycle records survive normal reloads and compatible app updates. Dismissing alerts or deleting old local records does not delete indexed portfolio history. An entry that exists only locally can disappear when its local record is removed.

When local records are deleted

A fully resolved flow becomes eligible for deletion seven days after its latest completion evidence. Cleanup runs when history loads and hourly while the app is open. It does not run in the background while the browser is closed.

The app deletes a flow's records together. It keeps pending or unknown outcomes, conflicting results, unfinished sequences, and pending balance refreshes. If a bridge's source transaction succeeded but the requested action failed, a confirmed refund is required before expiry. Time passing alone does not resolve an uncertain transaction.

Deletion leaves a small marker containing the record ID. This prevents a stale tab from restoring the deleted transaction data. These markers remain; the full transaction details are removed.

6 / What changed in the code.

The repository now separates shared transaction rules from app-specific connections. The lifecycle directory in packages/vault-widget contains the service, record model, outcome rules, and retention rules. The widget's preparation layer connects route-specific inputs to that service, and its transaction window reads the resulting progress.

Yearn supplies the persistent store, tab coordination, wallet and provider connections, balance updates, and activity views. Its server code supplies the Enso gateway and Redis coordination. This keeps browser and server infrastructure out of the shared transaction core.

The migration includes deposit and withdrawal paths, approvals, Enso sequences, app-specific migrations, reward and portfolio claims, and yvUSD actions. It removes the old planned controller, receipt-forwarding module, notification status writers, and separate source and bridge pollers from Yearn's active path. The unused use-indexeddb dependency is also removed.

The reusable widget still contains a legacy fallback for hosts without the required lifecycle capabilities. Yearn does not silently take that fallback when a required recipe is missing. Removing it depends on migrating those remaining hosts.

The branch adds a net 1,775 lines of implementation and configuration, and 2,394 lines of tests, compared with the implementation baseline. Documentation is excluded from these counts. The earlier Markdown plans are kept locally under the ignored docs/plans/ directory; this guide is the reviewer-facing document.

The smaller number of independent status writers is the main simplification. It does not make the service itself small: it is 1,085 lines at this snapshot. Record merging, preparation, and host integration still need careful review. The design makes those responsibilities explicit instead of spreading them across screens and notification code.

7 / What the checks establish, and what remains.

The checks run on 6 October 2026 passed 1,297 tests: 460 in the widget, 832 in Yearn, and 5 in yBOLD. Workspace TypeScript, lint, and both architecture boundary checks also passed. These checks used implementation commit bb1adf64. This document revision changes no application code.

The most useful tests check the boundaries between steps and systems. Reopening after approval must not send the final action twice. Failed history loading must block a fresh request. A Safe proposal must remain pending until execution and receipt confirmation. A bridge source receipt must not stand in for destination delivery. Conflicting saved evidence must remain unresolved.

Other tests cover late wallet responses, failed storage writes, balance-refresh errors, deleted records returning from stale tabs, alert acknowledgement, and pending rows becoming completed rows. Gateway tests check competing clients, shared delays, cached responses, and Redis response decoding.

Earlier checks included Yearn and yBOLD production builds, native Chromium storage and tab coordination, desktop and mobile activity, and isolated Upstash coordination tests. Wallet identity, receipts, or provider responses were simulated in those exercises. They demonstrate specific behavior; they do not establish real-wallet, Safe, or bridge parity.

Before merge, controlled external transactions must cover network switching, approval and continuation, reload recovery, Safe execution, replacement and cancellation, bridge delivery, and refunds. Outage tests must show that tracking can recover without resending. Production instances must share the correct bridge Redis configuration.

The bridge path is active on this branch and has no rollout flag. A rollback therefore needs more than returning to an older build: pending references must remain readable, and tracking must have a compatible recovery path. Approval grouping and removal of remaining host fallbacks are also still open. The PR remains a draft.
